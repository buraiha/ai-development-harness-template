# AI Development Harness Template

CodexなどのAI開発エージェントに、リポジトリ内での仕事の進め方を共有するための汎用テンプレートです。

特定の言語やフレームワークには依存せず、次の流れを共通化します。

```text
要求理解 → 調査 → 変更方針 → 実装 → 検証 → 必要な修正 → 最終確認 → 報告
```

## 推奨構成例

```text
AGENTS.md
VERSION
CHANGELOG.md
.ai/
├── README.md
├── common.md
├── project.md
├── guides/
│   ├── 01-requirements.md
│   ├── 02-design.md
│   ├── 03-implementation.md
│   ├── 04-testing.md
│   └── 05-review.md
└── tasks/
    ├── README.md
    ├── 0001-add-authentication.md
    ├── 0002-add-user-pricing-table.md
    └── 0040_0010-add-auth-data.md
docs/
├── requirements.md
├── architecture/
├── specifications/
└── decisions/
```

`0001-add-authentication.md`、`0002-add-user-pricing-table.md`、`0040_0010-add-auth-data.md`、`docs/` 配下は導入先で必要に応じて追加する例であり、このテンプレートには含まれていません。`VERSION` と `CHANGELOG.md` は各導入先の初期値を確定して作成し、テンプレート原本の値や履歴をコピーしません。

- `README.md`: 人間向けの概要と利用方法
- `AGENTS.md`: AIが最初に読む入口、基本原則、指示の優先順位
- `VERSION`: バージョンの正本（初期開発は `0.0.1`、既存プロジェクトはユーザー指定の開始値）
- `CHANGELOG.md`: バージョンごとの日本語の変更履歴
- `.ai/common.md`: プロジェクトを問わない共通の作業ルール
- `.ai/project.md`: AIの判断へ直接影響する、最小限のプロジェクト固有ルール
- `.ai/guides/`: 要求整理、設計、実装、テスト、レビューの再利用可能な手順
- `.ai/tasks/`: 機能追加や変更ごとの個別実装指示書。このリポジトリ自身の保守taskも含む
- `docs/`: 現在有効な詳しい仕様、設計、重要な意思決定

## 新規・既存の両方で使う

同じハーネスを使い、AIが依頼と作業対象の実態から進め方を判断する。ユーザーによるモード指定は不要。既存部分は契約と互換性を守り、未実装部分は必要十分な初期設計・構成・検証手段を用意し、混在する場合は接続部分も確認する。未決・未整備の事項はその状態を明記し、決定や検証後にproject.mdへ反映する。

実装依頼には必要なtaskの作成と進捗・検証結果の記録を含む。要求や受け入れ条件をAIが勝手に変更する権限は含まない。

## 要件定義から開発を始める

新規プロジェクトでは `docs/requirements.md` を現在有効な要件の正本として作成します。既存の正本がある導入先では、その配置を維持します。
要件定義書の作成・更新だけの依頼に専用taskは不要です。READMEは背景と概要、requirementsは現在の要件、taskは個別作業の指示・結果として役割を分けます。

要件には対象・対象外、機能、制約、対応環境、要件ID、受け入れ条件、未決・未検証事項を記載します。
実現方法の候補と合意済みの要求を区別し、要件への合意を実装・環境変更の包括的な承認とは扱いません。
設計・実装が依頼されたら、対象要件IDと受け入れ条件を参照する個別taskへ引き継ぎます。

詳しくは [要件定義ガイド](.ai/guides/01-requirements.md) を参照してください。

## 個別タスクの使い方

`.ai/tasks/` には、ひとまとまりの開発内容ごとに指示書を作成します。機能追加や大きな変更だけでなく、軽微な修正でも、変更を始める前にtask文書を用意します。ユーザーが指定する方法と、依頼を受けたAIが先に作成する方法のどちらでも構いません。ただし、要件定義書の作成・更新だけの場合は上記の例外に従います。

新しい独立taskのファイル名は `4桁の連番-開発内容.md` とし、開発内容には英小文字の kebab-case を使用します。親taskを分割する場合は、`親taskID_4桁の子番号-開発内容.md` として子taskを作成できます。

```text
0001-add-authentication.md
0002-add-user-pricing-table.md
0003-add-pricing-settings-ui.md
0040_0010-add-auth-data.md
```

task文書は完全な実装手順書ではありません。目的、期待する結果、守るべき点が分かれば、既存実装を調査して判断できる実現方法や細部には曖昧さを残せます。軽微な修正では、必要な項目だけを使った短いtask文書で構いません。

標準的には、次の内容を記載します。

- 状態と依存するタスク
- 実装する目的と要求
- 変更対象と対象外
- 守るべき既存仕様や制約
- 受け入れ条件
- 想定する検証方法

AIへ作業を依頼するときは対象のtaskファイルを明示します。独立taskでは先頭の4桁、子taskでは親task IDと子番号を結合した部分を完全なtask IDとして扱います。実行順序や依存関係は本文へ明記し、指定されていないtaskは自動的な実装対象になりません。

実装後は人間が試験し、必要な修正があれば、原則として該当taskへ追記してからAIへ修正を依頼します。人間が直接更新せず、AIへtask文書への反映と修正を一度に依頼しても構いません。動作や仕様が固まったら、確定した要求、修正内容、受け入れ条件などをtask文書へ反映します。

task文書は個別の指示と実装後に確定した内容の記録です。完了後も有効な仕様や設計は `README.md` または `docs/` に反映し、task文書だけを現在の仕様の根拠にしないでください。

## 導入方法

1. 対象ファイルが未配置の場合は `AGENTS.md` と `.ai/` を配置します（テンプレート自身の保守taskは除く）。既存ファイルがある場合は、後述の導入・更新手順に従って差分を統合します。
2. `.ai/project.md` のプレースホルダーを、対象プロジェクトで確認できる事実に置き換えます。
3. 詳しい仕様や設計は、対象プロジェクトの `README.md` または `docs/` で管理します。
4. バージョン管理が必要な時点で、共通ルールに従い開始値・保存先・互換性の判断対象を設定します。
5. 個別の実装依頼では、AIが変更前に必要なtaskを用意します。リリース対象のロジック変更の採番は、試験完了後・リリース前のコミット直前に行います。

最小構成で始める場合は、`.ai/common.md` の必要な要点と短い `Project Specific Rules` を `AGENTS.md` に統合します。その場合は、存在しない `.ai/common.md`、`.ai/project.md`、`.ai/guides/`、`.ai/tasks/` を必須とする記述も、実際の構成に合わせて削除または調整してください。現在の `AGENTS.md` だけをそのままコピーする方法ではありません。

## 既存プロジェクトへの導入・ハーネスの更新

ハーネスの導入・更新時は [導入ガイド](.ai/README.md) の「既存プロジェクトへの導入・ハーネスの更新」に従ってください。

## バージョンと変更履歴の管理

リリース対象のロジック変更だけをバージョニングします。試験完了後・リリース前のコミット直前に採番とコミットの承認を得て、リリース完了と実際のリリース日の記録をもってバージョニング作業を完了します。文書整備・調査・記録だけの作業は対象外です。保存先・採番・チェンジログの手順は [共通ルール](.ai/common.md) の「バージョンと変更履歴」にまとめています。

## 設計書と実装が一致しない場合

AIは差分の大きさではなく、根拠・仕様判断の必要性・影響でレベル0〜3を判定します。表現差や承認済みの根拠で解決できる差は依頼範囲内で扱い、未合意の仕様判断が必要な差は依存する変更を止めて確認します。重大な影響がある場合は影響する操作・検証も停止します。安全な調査や独立した作業は継続できます。詳細は [共通ルール](.ai/common.md) を参照してください。

## 方針

- 既存実装を調査してから変更する
- 要求を満たすための必要最小限の変更に留める
- ユーザーの既存変更や未追跡ファイルを保護する
- 既存の検証手段を調査して使用する
- 未確認事項を確認済みとして扱わない
- 明示的な依頼なしにコミット、プッシュ、デプロイ、本番操作を行わない

AIによるリリースはユーザー指定の専用チャットで、操作内容を復唱して許可を得てから実行します。他のチャットでは移動を案内します。人が自分で行う手動リリースは対象外です。専用チャットの識別情報は `.ai/project.md` に記録します。これはAIの行動ルールであり、手動操作を技術的に制限するものではありません。

詳しい導入方針は [`.ai/README.md`](.ai/README.md) を参照してください。
